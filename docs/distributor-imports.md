# Distributor CSV settlement import (MOE-005)

This is a **manual exported-file normalization** contract, not a live TooLost connection. The provider's exact export schema must be verified against a real authorized export before supplying explicit column mappings. Imported rows are not automatically recognized revenue, paid royalties, or ledger disbursements.

Call `parseDistributorStatement(csv,{labelId,source,mapping})` with explicit header names for transaction identifier, date, ISRC, currency, gross, fees, net and payout status. A settled row also requires a settlement-reference column. Exact decimal strings become integer minor-unit strings without floating-point rounding, grouped by their original currencies.

The importer fails closed on duplicate transaction IDs, missing headers, invalid ISRC/date/amount, inconsistent gross/fee/net, and unsupported payment states. It produces stable per-label/source/transaction identities, provenance `imported_csv`, and `isLive:false`. Downstream catalog resolution, bank/invoice settlement reconciliation, transactional persistence, reversals, and signed authorized provider feeds remain required for full MOE-005 acceptance. The parser explicitly supports USD, EUR and GBP at two decimal places, JPY at zero, and KWD at three; it rejects every other currency until its exponent and arithmetic are implemented and verified. ISO 4217 minor units are maintained by [SIX](https://www.six-group.com/en/products-services/financial-information/market-reference-data/data-standards.html); [the Bank of Japan lists the one-yen coin](https://www.boj.or.jp/en/note_tfjgs/note/valid/issue.htm), and [the Central Bank of Kuwait defines 1,000 fils per dinar](https://www.cbk.gov.kw/en/banknotes-and-coins/banknotes/introduction). a three-letter shape alone does not establish the exponent.

A scoped ingest credential can POST `/v1/distributor/statements` with `labelId`, `source`, a stable `statementId`, `csv`, and `mapping`. The whole statement is committed atomically. Each ISRC must resolve to exactly one track in that label; a missing or ambiguous catalog link aborts the import. Replaying the same statement or transaction is idempotent; reusing either identity with changed content returns a conflict. Scoped readers can GET `/v1/distributor/rows` and inspect the original provider status, catalog IDs, exact amounts, and import time. The provider's `settled` status and reference remain claims from an imported file, not bank-verified settlement or recognized revenue. Bank/invoice reconciliation, reversals and correction workflow remain outstanding.

An authorized manager may POST `/v1/distributor/reconciliations` with `labelId`, `source`, a provider `settlementId`, `invoiceId`, `invoiceMinor`, `bankTransactionId`, and `bankMinor`. The engine checks one currency and exact equality between imported provider net, invoice, and recorded bank amounts; it rejects missing rows, reversals, duplicate invoice/bank references and conflicting replay. The GET endpoint returns records within the reader's label/source scope and a `currentSourceMatch` recomputation so later imports cannot silently keep an outdated match. `evidenceStatus: operator_recorded_amount_match` describes an arithmetic match of supplied references; it does **not** verify a bank account, invoice authenticity, payout receipt, or royalty disbursement. Those external checks remain required before financial recognition.

Corrections use a new distributor transaction ID. A `reversed` row must supply `reversesExternalId` in its explicit mapping, carry a negative net, and exactly negate one prior positive transaction for the same label, source, ISRC and currency. A unique constraint permits one full reversal per original. The import transaction verifies references after inserting all rows, so an out-of-order original and reversal in one file is safe; missing/mismatched originals roll back the entire file. A reversal also makes an earlier recorded settlement amount match stale in the read API.
